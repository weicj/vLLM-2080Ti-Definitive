# v0.2.1-pre4 SM75 测试征集

语言：[English](0.2.1-pre-testing-call.md) | [简体中文](0.2.1-pre-testing-call.zh-CN.md)

`v0.2.1-pre4` 是 vLLM 2080 Ti Definitive Edition 面向 SM75 的 nightly 对齐公开测试候选。它是预发布版本，不是稳定生产基线；持续维护的 `0.1.x` 线仍是项目当前的稳定发布主线。

Release candidate：0.2.x 维护分支上的 `v0.2.1-pre4`。

需要发布简短 Issue 正文时，请使用[测试征集模板](0.2.1-pre-issue-body.zh-CN.md)。

本文用于集中收集真实硬件上的构建、正确性、CUDA Graph、模型路线、容量和性能证据。
仅能加载模型并不代表该模型已经成为可推荐的部署路线。

维护分支：[`vllm-2080ti-definitive-0.2.x`](https://github.com/weicj/vLLM-2080Ti-Definitive/tree/vllm-2080ti-definitive-0.2.x)。
`v0.2.1-pre` tag 保留首个公开预发布快照；后续 0.2.x 的验证修复和 profile 会进入此维护分支。
默认分支与 `v0.1.x` 仍然是稳定的 CUDA 12.8 兼容线。

## 版本范围

本版本将硬件定向 fork 迁移到一套新的运行时目标：

| 组件 | `v0.2.1-pre4` 目标 |
| --- | --- |
| 上游基线 | nightly `b23433088b`（`v0.29.1rc0-33`） |
| CUDA ABI | `13.0` / `cu130` |
| PyTorch | `2.13.0` |
| Python | `3.12` |
| 目标主机 | Ubuntu `26.04+`、Linux kernel `7+`、GCC/G++ `15` |
| 主要硬件 | 双 RTX 2080 Ti 22 GB、NVLink、TP=2、SM75 |

维护中的 `v0.1.x` 仍然是 CUDA 12.8、PyTorch 2.11、较早 kernel 和 GCC 12/13/14
的兼容路线。这些环境不是本预发布版本中的安装时切换选项。

## 为什么跟随 vLLM nightly

`v0.2.1-pre4` 的价值不只是刷新 CUDA ABI。它延续了从 `v0.1.15` 的 vLLM
`0.21.0` 时代运行时迁出的工作，并把保留的 SM75 改动对齐到当前 upstream nightly。
Qwen3.x、MTP、混合 attention 和非 eager CUDA Graph 所依赖的上游代码仍在实质变化，
因此 pre4 优先采用上游修复，而不继续堆积本地 backport。下文 pre3 性能数据仅是历史
记录，必须在 pre4 上重新运行后才可晋升路线。

| 维度 | 稳定 `v0.1.x` 兼容线 | `v0.2.1-pre4` 迁移目标 |
| --- | --- | --- |
| 上游/运行时基线 | vLLM `0.21.0` 时代运行时 | nightly `b23433088b`（`v0.29.1rc0-33`）的 V1 运行时契约 |
| 环境 | CUDA 12.8、PyTorch 2.11、较早 kernel / GCC 支持 | CUDA 13.0、PyTorch 2.13、Python 3.12，以及 Ubuntu 26.04+/kernel 7+/GCC 15 目标 |
| 模型与服务集成 | 保留已验证路线 | 面向 Qwen3.8 时代模型/运行时的当前集成和维护中的 V1 服务接口 |
| 图与推测执行 | 保留的 SM75 图策略 | 当前图捕获、调度器、推测解码和压缩 KV 执行契约 |
| Attention / kernel 工作 | 既有 FlashInfer / FlashQLA / Triton 集成 | 在新运行时复验 FlashInfer、FlashQLA 的 SM75 路径，并继续推进 TurboQuant K8V4 MTP3 |
| 维护方式 | 后续 fork 修改会继续堆积在旧栈 | 保持 SM75 fork 改动小且有 guard，并跟随明确的上游 release 基线 |

这次 rebase 带来的具体上游代码变化，是单纯升级 CUDA 不会带来的：

- **V1 调度与图执行：** 统一 scheduler、chunked prefill、prefix cache 计账、speculative
  decoding、`FULL_AND_PIECEWISE`/piecewise CUDA Graph 策略、Model Runner V2 以及
  breakable/dynamic graph 形成了同一套执行契约。当前 shipping 的 `normal` 和 `fast`
  profile 依赖的是这套契约，不等价于在 vLLM `0.21.0` 下更换编译器或 toolkit。
- **Qwen3.x 与 MTP 模型契约：** 上游加入 Qwen3.5 dense/MoE 模型支持、Qwen MTP 加载和
  EAGLE3/speculator 集成、GPTQ-MTP 修复，以及多模态 ViT CUDA Graph 支持。这些是
  Qwen3.8/Qwen3.x 验证路线所依赖的当前模型和 assistant-model 接口。
- **混合 Mamba/GDN 与 KV cache 语义：** 上游重构 hybrid attention，统一 KV cache
  layout/specification，修复 Mamba 对齐和 partial prefix-cache 行为，并使 hybrid 模型
  能与 speculative decoding 协同。这些直接影响 Qwen3.x GDN 路线，不能靠环境变量安全补齐。
- **TurboQuant 与压缩 cache 正确性：** 上游加入 KV mode 处理，并修复 CUDA Graph 捕获前
  预留 TurboQuant workspace 的问题。缺少这类代码变化时，旧路线可能只锁定 5 MiB workspace，
  后续 8 MiB continuation prefill 就会失败。

代表性的上游变化包括：[Qwen3.5 模型支持（#50210）](https://github.com/vllm-project/vllm/pull/50210)、
[Qwen3.5 ViT 全 CUDA Graph（#42151）](https://github.com/vllm-project/vllm/pull/42151)、
[支持 full CUDA Graph 的 dynamic speculative decoding（#45953）](https://github.com/vllm-project/vllm/pull/45953)、
[统一 hybrid KV-cache layout（#44455）](https://github.com/vllm-project/vllm/pull/44455)，以及
[捕获前预留 TurboQuant workspace（#44053）](https://github.com/vllm-project/vllm/pull/44053)。
这些只是代表性上游变化，并不表示所有上游 feature 都自动适用于 SM75。

因此，这次是 ABI、scheduler、模型契约和 kernel 集成的迁移，不是单纯 toolkit 升级。
SM75 特有行为仍然会被明确 guard，不能描述为上游 vLLM 的通用行为。

现有受控对比已经说明这次迁移具备实际价值：固定双 2080 Ti NVLink、Qwen3.8-27B-FP8、
TP=2、FP16 KV、单请求 4K/128 和非 eager CUDA Graph 后，FlashInfer + FlashQLA 的
MTP3 路线从 `v0.1.15` 的 `1453.46 / 60.70` 提升到 `v0.2.1-pre2` 的
`1522.72 / 75.83` prefill/decode tok/s；对应 noMTP 为 `1420.07 / 30.01` 与
`1570.57 / 30.01`。完整测试方法、实际 graph mode 和质量结果见
[迁移验证报告](2080ti-0.2.1-pre-validation.md)。

pre3 曾加入 Qwen3.8-27B-NVFP4 的严格并发 4K/128 路线。在 TP=2、无 MTP、
非 eager CUDA Graph、FP8 KV、关闭 prefix cache，并使用
`fp8kv-16K-nomtp-concurrent.env` profile 时，并发 `1 / 2 / 4 / 8` 的完整窗口
aggregate decode 是 `41.53 / 79.94 / 151.19 / 269.30 tok/s`。窗口从第一个请求
首 token 开始，到最后一个请求完成结束；C8 首 token spread 为 1.447 ms。

这些数字只是一个固定且受控路线的证据，不表示 rebase 后所有 checkpoint 或量化路线都会自动更快。每个 profile 仍必须独立通过质量探针、非 eager CUDA Graph capture/replay、容量和 4K/128 验证。对于旧 CUDA 12.8 / PyTorch 2.11 环境，持续维护的 `v0.1.x` 线仍是受支持的稳定选择。

## 本版本升级内容

### 上游迁移和 SM75 构建

- 对齐上游 nightly `b23433088b`（`v0.29.1rc0-33`），保留 CUDA 13.0 / PyTorch 2.13 依赖栈。
- 新增目标环境感知的构建路径：创建独立 `.venv`、编译请求的 SM75 架构、记录构建
  日志，并在编译器、kernel 或 CUDA toolkit 不符合目标时明确失败。
- 恢复 `v0.1.x` 的资源感知构建并行策略：`build.sh` 根据 CPU 线程、系统内存和可配置
  的 `BUILD_AUTO_MAX_JOBS_CAP`（默认 `8`）选择安全默认值；`MAX_JOBS` 和
  `BUILD_MAX_JOBS` 仍可由用户显式覆写。
- 保留双 2080 Ti 所需的 launcher、路线 profile、验证报告和 benchmark 证据。

### 非 eager 的 SM75 服务路线

- 在目标 Qwen checkpoint 通过原生 paged prefill/decode 验证后，恢复 SM75 的
  FlashInfer 能力和优先级路线。
- GDN prefill 保留 FlashQLA legacy forward 扩展。patch、构建和启动都会检查
  `gdn_forward` 与 `gdn_forward_varlen` 两个接口，旧缓存 `.so` 不会再被当成可用扩展
  进入多请求 prefill；只有超出 packed metadata 支持范围的调用才继续使用 Triton/FLA
  fallback。
- 已验证 `enforce_eager=False` 下的 CUDA Graph capture；eager 仅用于排障，不能
  作为部署性能路线。
- 补充混合显卡机器的选择规则：launcher 会通过 `nvidia-smi` 把数字形式的
  `GPU_DEVICES` 转换为物理 GPU UUID 后再导出，也接受直接填写 UUID。
  查看物理索引和拓扑时仍建议设置 `CUDA_DEVICE_ORDER=PCI_BUS_ID`。
- no-MTP 路线使用小型 decode CUDA Graph ladder（8 路 profile 为
  `[1,2,4,8,16]`）。`MAX_NUM_BATCHED_TOKENS` 保持为 piecewise 编译预算，不再
  作为大 CUDA Graph capture size，避免首次请求被长 prefill JIT 污染。
- 单机 V1 multiprocessing/uniprocess executor 使用无冲突的 PyTorch `FileStore`
  rendezvous；多机和 data-parallel group 继续使用 TCP。专项测试 3/3 通过，`.31`
  上的干净 TP2 smoke 也完成了 NCCL 初始化和一次生成请求。

### 量化、MTP 和正确性工作

- 在 SM75 上验证 Marlin weight-only 的 FP8、INT4 和已生成的 NVFP4 子集。
- 恢复 TurboQuant K8V4 MTP3 候选使用的 fused B=4 compressed-cache decode。
  普通 continuation prefill 仍使用 raw-K/V merge；SM75 raw-K/V B=4 graph 路线
  仍未提升，因为图捕获时可能发生错误。
- 增加 Qwen GDN 的 SM70/SM75 packed-varlen FlashQLA prefill，并加入
  `--prefill-batch-barrier` 共享 prefill frontier，让同步 cohort 共同提交最后一次
  prefill。TurboQuant 会按 request 规划 mixed first-chunk wrapper，Qwen GDN 纯
  prefill 复用调用方 output buffer。
- 针对 issue #112 的 INT6/AutoRound 加载问题锁定 `humming-kernels[cu13]==0.1.13`。
  完整 Minachist checkpoint 尚未在 `.31` 上复测。
- 覆盖 GDN state slot zero / padded slot、Mamba 对齐和 external-hit resume、CPU KV
  offload store/load 与 partial-hit scheduling 回归。
- 加入 launcher 和 profile 校验工具。

## 已知限制与待完成工作

1. **MXFP4 目前不支持 SM75。** 上游 MXFP4 专用 Marlin kernel 仅面向更新的架构
   生成。通用 FP4 capability check 返回成功，不表示 SM75 MXFP4 kernel 存在。
2. **TurboQuant K8V4 依赖具体 checkpoint。** 当前 Unsloth Qwen3.8 NVFP4 纯文本
   profile 已通过质量门槛并记录在上表；旧候选 checkpoint 以及多模态/FP16-KV
   组合仍需单独验证，不能自动继承当前结果。
3. **Qwen3.6 GPTQ-Marlin MTP3 在 `gpu_memory_utilization=0.96` 时可能 OOM。**
   较低利用率的工程测试可以执行，但尚未通过所有质量门槛。
4. **Qwen3.x 35B FP8 只保留 normal 兼容路线。** normal 模式的 FP16 KV 纯文本和
   图文 preset 已通过 CUDA 13.0/pre3 门槛；aggressive/fast 测量没有性能收益，因此不
   作为 shipped profile。
5. **真并发 profile 默认不启用。** 它是有边界的同步长 prompt 吞吐路线，不是默认
   多租户服务策略；严格 aggregate 指标覆盖从首个首 token 到最后完成的完整窗口，
   本对比必须关闭 prefix cache。
6. **TurboQuant 的 CUDA-graph-safe wrapper cache 仍有生命周期限制。** 默认 bounded
   LRU 路径已经验证；设置
   `VLLM_TURBOQUANT_FLASHINFER_PREFILL_CUDAGRAPH_SAFE=1` 会故意关闭 eviction，
   仍需独立验证。

关于 #112 和 #135 的详细证据，包括长上下文运行和 Humming 依赖跟进，见
[问题验证记录](issue112-135-validation-20260827.md)。

## 如何测试

请获取 0.2.x 维护分支，不要假设它是默认分支。若需要首个预发布快照，
`v0.2.1-pre` tag 仍然可用：

```bash
git clone https://github.com/weicj/vLLM-2080Ti-Definitive.git
cd vLLM-2080Ti-Definitive
git fetch origin vllm-2080ti-definitive-0.2.x
git switch --track origin/vllm-2080ti-definitive-0.2.x

./build.sh
```

`build.sh` 会自动选择默认并行度。只有在评估过构建主机可用 CPU 和内存后，才应设置
`MAX_JOBS` 或 `BUILD_MAX_JOBS`；显式值会覆盖自动选择结果。

非交互式双卡启动时，请按本机物理 2080 Ti 的 ID 选择 GPU。launcher 会在导出前把
数字 ID 转换为物理 UUID；下面的 ID 仅为示例：

```bash
CUDA_DEVICE_ORDER=PCI_BUS_ID \
MODEL_DIR=/path/to/checkpoint \
PROFILE=2x2080Ti/qwen27b/w8a16/fast/tqk8v4-256K-mtp3-text-only.env \
MODE=fast GPU_DEVICES=0,1 TP_SIZE=2 \
NON_INTERACTIVE=1 ./launcher.sh
```

若覆盖 profile 参数，请先执行 `./launcher.sh --print-config`。性能和 CUDA Graph
验证必须保持 `enforce_eager=False`。

## 希望大家重点测试的内容

### 构建和环境

- CUDA 13.0 / PyTorch 2.13 在目标主机上的构建。
- SM75 Marlin extension 的生成与加载。
- 构建失败、编译器/kernel/toolkit 诊断、构建耗时、内存压力，以及自动选择或显式覆盖
  的并行任务数。

### 服务与正确性

- launcher 启动、health check、`/v1/models` 和连续请求稳定性。
- CUDA Graph capture/replay，以及 illegal address、graph replay、workspace 和 OOM。
- noMTP / MTP3 输出质量：重复、乱码、提前停止、仅 hidden-thought、reasoning parser
  和 tool calling。
- 长上下文、多轮对话、多模态；请报告实际可用上下文，而不是只报告配置上限。

### 模型和 KV 路线

- Qwen3.8 FP8、NVFP4 和 INT8 W8A8。cyankiwi AWQ-INT4 checkpoint 的量化元数据和
  tokenizer 不完整，因此不纳入已发布路线。
- FP16 KV、INT8 KV、TurboQuant K8V4；有条件时分别测试 noMTP 与 MTP3。
- Qwen3.x 35B FP8；请作为独立兼容路线并提供完整 checkpoint metadata。

### 性能测试口径

正确性探针应在请求的 chat-template kwargs 中关闭 thinking
（`{"enable_thinking":false}`），避免较短的质量预算全部消耗在隐藏思考段；这不会
改变服务 profile 或 launcher 配置。基准短测形状是单请求、tokenizer 计数后恰好 4096 token 的合成 prompt，以及
`max_tokens=128`。测试使用 TP=2、三次独立测量和非 eager CUDA Graph 执行。
这里的 4K/128 是 token 形状，不是 4K 个字符，也不是固定的一段自然语言 prompt。

为了便于对比，请先说明是否使用了上述基准形状，再报告模型和权重格式、KV dtype、
MTP、profile/mode、请求并发、CUDA Graph 模式和三次独立测量。请分开提供 prefill
tok/s、decode tok/s、峰值显存和 MTP acceptance rate；只给一个总速度没有意义。
